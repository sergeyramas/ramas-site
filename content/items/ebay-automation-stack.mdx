## Это не кейс под клиента — это мой бизнес

Проговорю прямо: то, что описано на этой странице, — не пилотный проект и не демо для портфолио. Это инфраструктура, на которой прямо сейчас держится мой собственный reseller-бизнес на eBay в США. Я оператор и единственный бенефициар, а не подрядчик, который сдал систему и ушёл. Поэтому все цифры и решения ниже — не из презентации, а из продакшна, где на кону мои собственные деньги и мой собственный инвентарь.

Ниже по странице есть предложение поставить похожую систему вам — это отдельный разговор. Но сначала — как это устроено у меня.

## Зачем это нужно

Классическая боль reseller'а на eBay:

- Заказ оплачен → надо вручную закрыть сделку, проставить статус, написать покупателю
- Поставщик отгрузил → надо вручную взять трек и вбить в eBay
- Цена у поставщика прыгнула → твой листинг становится убыточным, а ты узнаёшь спустя неделю
- Товар закончился → продал то, чего нет → strike по аккаунту → ban
- 20 одинаковых писем покупателям про tracking и refunds → заняты вечера

При **20-50 заказах в день** всё это превращается в полноценную работу на 6-8 часов. У одного человека — до 30 заказов потолок без выгорания. Стэк убирает эту ручную работу полностью и масштабирует **в 5-10 раз** на одного оператора.

## Что входит в стэк

Пять автономных ботов, отдельный верификатор перед каждой оплатой и контрольная панель в Google Sheets и Telegram.

### 1. Closing-автомат

Слушает eBay через Trading API. Как только покупатель оплатил — заказ автоматически:
- Помечается как Paid
- Триггерит Purchasing-bot (см. ниже)
- Записывает SKU + параметры заказа в Google Sheets
- Шлёт алерт в Telegram (для оператора, на случай если что-то пошло не так)

Время от платежа до закупки у поставщика — **под 60 секунд** в среднем.

### 2. Purchasing bot

Самая нетривиальная часть. По SKU из заказа знает, у какого поставщика брать товар (карта `SKU_CATALOG` в Google Sheets — про неё ниже). Бот:
- Открывает сайт поставщика (несколько B2B-каталогов + Shopify-магазины — конкретный список под NDA)
- Логинится под сохранённой учётной записью магазина
- Кладёт товар в корзину
- **Подменяет shipping-адрес на адрес покупателя eBay** (ключевая dropshipping-механика)
- Проходит проверку у отдельного агента-верификатора и только после аппрува платит корпоративной картой (подробности — в разделе «Верификация перед оплатой» ниже)
- Сохраняет supplier order ID в Sheets

Для каждого поставщика — свой адаптер (текущих — 4, добавление нового занимает ~2 часа). Полная автономность: ни одного клика человеком в стандартном случае.

### 3. Tracking sync

Опрашивает поставщиков по supplier order ID. Как только трек появился:
- Прокидывает его в eBay через Trading API → статус заказа обновляется
- Автоматически отправляет покупателю message с tracking
- Помечает в Google Sheets дату отгрузки и ожидаемую дату доставки

Покупатели получают информацию **раньше**, чем у обычных reseller'ов — за это растут seller metrics и Top Rated статус.

### 4. Price/stock monitor

Каждые N часов сверяет каждый твой листинг с источником у поставщика:
- Цена выросла → пересчитывает с учётом маржи и обновляет на eBay
- Цена упала → опционально снижает у тебя (более конкурентный листинг)
- Out of stock → автоматически скрывает листинг (`hide` вместо `delete`, чтобы сохранить sales history)
- Вернулся в наличие → автоматически снимает hide

Защищает от стрика «продал то, чего нет» — главной угрозы reseller'у на eBay.

### 5. Buyer messaging via Trading API

Сообщения покупателю шлются программно — без захода в eBay UI. Отдельные сценарии:
- **Apology** — извинение при задержке
- **Refund explanation** — объяснение возврата с причиной
- **Tracking** — отправка трек-номера
- **Follow-up** — после доставки (просьба о feedback'е)
- **Custom** — на любую input-фразу (используется AI-агент с контекстом ордера)

Все сообщения логируются в Google Sheets для compliance и audit'а.

## Верификация перед оплатой — отдельный агент, не чекбокс

Самый рискованный момент во всей системе — не закупка сама по себе, а секунда, когда бот собирается списать деньги с корпоративной карты. Одна ошибка — не тот товар, не та модель, не тот адрес — и ты либо теряешь деньги, либо получаешь посылку в никуда.

Поэтому перед КАЖДОЙ оплатой заказ проходит через отдельного агента-верификатора — не тот же бот, что наполняет корзину, а независимая проверка со своим правом вето. Она сверяет:
- **Товар и модель** — то же ли SKU, что заказал покупатель, лежит в корзине у поставщика
- **Цену и маржу** — сделка всё ещё прибыльна с учётом текущей цены поставщика
- **Адрес доставки** — совпадает с адресом покупателя на eBay, а не с дефолтным адресом аккаунта
- **Платёжный гейт** — отдельное подтверждение CVV, которое не проходит, пока все проверки выше не зелёные

Это самая сложная верификация во всём стэке — сознательно избыточная, потому что цена ошибки здесь не «переделать», а реальные деньги с реальной карты. Оплата уходит только после аппрува по всем пунктам. Если что-то не сходится — заказ зависает и падает алертом оператору в Telegram, а не улетает вслепую.

## Playwright-агенты на удалённом сервере

Часть поставщиков не даёт API для закупки — только обычный сайт-магазин. Для них закупка идёт через headless-браузер на Playwright, который крутится на выделенном сервере и работает круглосуточно, не завися от того, включен ли у меня ноутбук.

Когда Purchasing bot получает заказ, Playwright-агент на сервере:
- Заходит в магазин поставщика под сохранённой сессией
- Находит нужный товар и кладёт в корзину
- Проходит чекаут, подставляя адрес покупателя вместо своего
- Доводит заказ до экрана оплаты и передаёт эстафету верификатору (см. выше)

Человек в этой цепочке не участвует вообще — ни разу не открывает сайт поставщика руками. Единственный след для человека — алерт в Telegram, если браузер застрял (поставщик поменял вёрстку, вылезла капча, слетела сессия) и нужен ручной разбор.

## Админ-панель — где оператор всё видит и решает

Весь контур завязан на одну точку правды, а не разбросан по головам разных сервисов и вкладок. Это связка из двух интерфейсов:

- **Таблица (Google Sheets)** — каждый заказ, его статус, к какому поставщику он привязан, когда закуплен, когда пришёл трек, сколько денег в обороте. Сюда же пишется каталог SKU → поставщик, по которому боты понимают, где что покупать.
- **Telegram-бот** — живой канал управления: сюда падают алерты (застрявшая закупка, подорожавший поставщик, странный buyer-кейс), отсюда оператор может остановить закупку, подтвердить спорное решение или спросить бота, что происходит с конкретным заказом прямо сейчас.

Закупка не запускается в вакууме — она триггерится и контролируется из этой панели: видно, какой заказ в очереди, какой уже идёт к оплате, какой ждёт решения человека. Это и есть те самые 15-20 минут в день — не копание в логах на сервере, а работа из одного экрана.

Админка не в разработке и не на бумаге — она сделана и работает с начала месяца: каждый заказ в этом периоде прошёл именно через неё, а не через ручной разбор логов или таблиц вручную.

```

                   │   eBay (US)     │
                   │   2 аккаунта    │
                   └────────┬────────┘
                            │ Trading API
                ┌───────────┴───────────┐
                │                       │
        ┌───────▼────────┐    ┌─────────▼─────────┐
        │ Closing-автомат│    │ Tracking sync     │
        └───────┬────────┘    └───────────────────┘
                │
        ┌───────▼────────┐    ┌───────────────────┐
        │ Purchasing bot │◄───┤ SKU_CATALOG       │
        │ (4 адаптера)   │    │ (Google Sheets)   │
        └───────┬────────┘    └───────────────────┘
                │
       ┌────────┼────────┬────────┐
       ▼        ▼        ▼        ▼
   Supplier A   B       C        D
                │
        ┌───────▼─────────┐    ┌──────────────────┐
        │ Price/stock     │    │ Buyer messaging  │
        │ monitor (cron)  │    │ (Trading API)    │
        └─────────────────┘    └──────────────────┘
                │                       │
                └────────┬──────────────┘
                         ▼
                  ┌──────────────┐
                  │  Telegram    │
                  │  notifier    │
                  └──────────────┘
```

**Стек:**
- **Python 3.11** + asyncio для всех ботов
- **VPS** (Hetzner / DigitalOcean, ~$10/мес) — все процессы крутятся одним systemd-юнитом
- **Google Sheets API** — каталог SKU↔источник, статусы заказов, audit log
- **eBay Trading API** + Inventory API
- **Playwright** — для поставщиков без API (live-чаты, Shopify-витрины)
- **Telegram Bot API** — алерты в реальном времени
- **Redis** — координация между ботами, дедупликация событий
- **Postgres** — persistent state, retry queue для падающих закупок

Все секреты хранятся вне кода, репозиторий приватный.

## Полуавтомат: что делает робот, что человек

Стэк сознательно **полу-автоматический**, не **полный** — потому что 100% автомат на маркетплейсах = бан-риск. Граница между "робот" и "человек" вынесена осознанно.

| Действие | Робот | Человек |
|---|:---:|:---:|
| Закрытие оплаченных заказов | ✅ | |
| Закупка у поставщика | ✅ | |
| Подмена shipping address | ✅ | |
| Верификация перед оплатой | ✅ | |
| Tracking sync в eBay | ✅ | |
| Стандартные buyer messages | ✅ | |
| Мониторинг цен и stock | ✅ | |
| Скрытие OOS-листингов | ✅ | |
| **Добавление новых SKU** | | ✅ |
| **Решения по spike-ценам** (если supplier поднял на 30%+) | алерт | принимает решение |
| **Сложные buyer-кейсы** (defect, return, dispute) | drafts ответ | проверяет и отправляет |
| **Договоры с поставщиками** | | ✅ |
| **Стратегия каталога** (что добавить в линейку) | | ✅ |

В среднем оператор тратит **15-20 минут в день** на задачи из правой колонки. Остальное — алерты в Telegram, на которые надо просто отреагировать тапом.
